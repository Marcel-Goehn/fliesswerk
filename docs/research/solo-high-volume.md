# How solo high-volume developers trust agent PRs (as of 2026-11-27)

**Question (#153):** How do solo developers who ship hundreds to thousands of agent-written PRs a month set up their workflow so they can merge without reading every PR? What makes the agent say "a human must look at this", what do they still read, and what failure stories do they report?

**Method:**
- Primary sources first: the developers' own repos, which were read in full where it mattered (`cursor/plugins` pstack, `mattpocock/skills`, `EveryInc/compound-engineering-plugin`), plus their own blog posts and talk transcripts.
- Talk and podcast content I couldn't watch is taken from third-party summaries or transcripts and marked **(summary)**. Anything with no primary trace is marked **unverified**.
- Not tested hands-on.

## Short answer

Nobody in this group trusts an agent PR because they read it. They trust it because of three things:

1. **The environment makes bad code hard to write.** Lint rules, types and architecture bans come out of every correction they make.
2. **A different agent proves the behavior on the running app.** The evidence is artifacts (videos, screenshots, command output, traces), not a summary.
3. **A small set of irreversible actions always goes to a human.**

The human's reading moves from diffs to the system: standards, verification tooling, the evidence, and a short "attention" list. The question "does a human need to look?" is answered by **reversibility and blast radius**, not by diff size.

## 1. How they set up to merge without reading

### Lauren Tan / pstack: verification is the product

- **She doesn't read the code.** "I actually have my agents now automerging PRs for me … I woke up today and there were about 20 PRs landed, and I just reviewed them on main … I really don't look at the code anymore" ([transcript](https://sozai.app/transcript/spacex-ai-engineer-lauren-tan-part-1/)).
- **Corrections become deterministic checks, not prose.** "Whenever you're correcting your agent, think about how you can make that a deterministic check instead of adding another line to your rules" **(summary)**. Her "inverse pyramid" is widest at codebase design, then static analysis (lint, types, tests), then runtime and formal verification, with prose rules as the thinnest layer. Concrete bans: `useEffect` in product code; the two Electron processes may not import from each other, enforced by a dependency-graph analyzer. Lint error messages tell the agent the root-cause fix. About 99% of code comments are banned ([summary](https://www.teamday.ai/ai/lauren-tan-spacexsi-grok-bot-11000-agent-prs-lint-rules)). A review comment that keeps recurring is "a code smell" and should become a lint rule or CI check ([transcript](https://sozai.app/transcript/spacex-ai-engineer-lauren-tan-part-1/)).
- **A per-project verification skill.** `/create-verification-skill` writes Launch, Doctor, Drive, Evidence and Cleanup steps, plus a *feature map* indexing "what the app does and what result proves each feature works". The generator must prove the skill once end to end before handing it over, and `/maintain-verification-skill` re-audits it daily ([guide 06](https://github.com/cursor/plugins/blob/main/harness/pstack/claude-code/docs/guide/06-verify-and-ship.md)). Most of her token spend now goes to verification **(summary)**.
- **The agent that judges is never the agent that wrote the code.** "Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would." Verifiers post `PASS`, `PASS+NOTES` or `FAIL` ([Shipping playbook](https://github.com/cursor/plugins/blob/main/harness/pstack/claude-code/skills/poteto-mode/playbooks/shipping.md)).
- **A verdict is pinned to a patch.** After a rebase, `git patch-id` at the verdict SHA is compared with the current head. If the two differ beyond tests, docs or lint config, the PR needs a fresh verdict. Auto-merge is armed only "on a PR whose verdict covers its current head" ([Shipping](https://github.com/cursor/plugins/blob/main/harness/pstack/claude-code/skills/poteto-mode/playbooks/shipping.md)).
- **Re-verification scales with the change** (cost control). The full verifier swarm runs once at the code-ready head. "A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head, and a wording-only change gets none." Before merging, the owner asks whether trunk's changes can affect the patch, instead of rebasing on every trunk move ([Autopilot-full](https://github.com/cursor/plugins/blob/main/harness/pstack/claude-code/skills/poteto-mode/playbooks/autopilot-full.md)).
- **What blocks is narrow.** "Only a bug a user would hit, a failed gate, or a wrong shipped doc blocks, and everything else goes in a follow-up." A problem the base already has doesn't block ([Autopilot-full](https://github.com/cursor/plugins/blob/main/harness/pstack/claude-code/skills/poteto-mode/playbooks/autopilot-full.md), [worker.md](https://github.com/cursor/plugins/blob/main/harness/pstack/claude-code/skills/poteto-mode/worker.md)).
- **Trust is earned before the loop runs.** You've done the task by hand or watched it done, the agent has your tools, "every stage proves its work and can stop the line", and you've read transcripts and turned repeated failures into checks ([guide 07](https://github.com/cursor/plugins/blob/main/harness/pstack/claude-code/docs/guide/07-overnight.md)).
- **She aims automation at maintenance first.** Small bugs from the customer-feedback pipeline are reproduced, fixed and merged automatically overnight. Features get longer internal dogfooding ([Lightcone summary](https://www.teamday.ai/ai/roman-ugarte-lauren-tan-grok-bot-ai-coworkers-trust-ladder)). After release, an agent fuzzes the built app like a user, and each bug it finds gets a fix PR that is auto-merged **(summary)**.

### Peter Steinberger: close the loop, read architecture and dependencies

- "These days I don't read much code anymore … most code I don't read." He keeps the system's structure in his head. "The important decisions these days" are language, ecosystem and dependencies ("Is this well-maintained? … peer dependencies?") ([blog](https://steipete.me/posts/2025/shipping-at-inference-speed)).
- Agents call the tool directly and verify the output: "closing the loop". He runs tests locally through agents instead of waiting on remote CI ([blog](https://steipete.me/posts/2025/shipping-at-inference-speed), [show notes](https://newsletter.pragmaticengineer.com/p/the-creator-of-clawd-i-ship-code)).
- He commits straight to `main` and rarely uses worktrees or PRs, which he sees as added complexity ([blog](https://steipete.me/posts/2025/shipping-at-inference-speed)). Code review is "dead for this workflow", replaced by architecture discussions ([show notes](https://newsletter.pragmaticengineer.com/p/the-creator-of-clawd-i-ship-code)). He treats outside PRs as "prompt requests".
- **His suspicion signal is effort.** "When codex comes back and hasn't solved it in one shot, I already get suspicious" ([blog](https://steipete.me/posts/2025/shipping-at-inference-speed)).

### Matt Pocock: layered review, with the human gated by "door" and "blast radius"

- "I don't think you need to review every single line yourself … I'm interested in the system that produced it." He keeps QA for himself, ratchets a lint rule onto every pattern he dislikes, and has an automated review check the work against his coding standards ([post](https://www.aihero.dev/watch-me-ship-a-21-000-line-feature-with-mattpocock-skills~ez95n)).
- **Three layers** **(summary)**: cheap automated checks, then a separate review agent that holds the coding standards (kept out of the implementer's context), then human review reserved for high-risk changes. The review agent commits fixes instead of leaving comments ([talk summary](https://daily.dev/posts/fixing-the-pr-bottleneck-matt-pocock-aihero-jyn4aj6sm)).
- **Every PR carries a risk header (primary).** His `pr` skill's template ends with `## Merge Danger`, stating `**Door:** <one-way or two-way>` and `**Blast Radius:** <one word>`. "A PR that is cheap to roll back is lower risk. Changes that involve destructive actions or hard-to-reverse decisions are one-way doors." Evidence is tiered: "Screenshots are S-tier … Execution-based evidence is A-tier" ([`pr` skill](https://github.com/mattpocock/skills)).
- A huge PR gets split into stacked diffs, with the reversible changes first and the one irreversible change last ([post](https://www.aihero.dev/watch-me-ship-a-21-000-line-feature-with-mattpocock-skills~ez95n)).

### Kieran Klaassen / compound engineering: a review swarm whose cost scales with consequence

- `/workflows:review` ran 13 specialized reviewers in parallel ("while I made dinner"), and `/triage` ranks the findings by severity for accept or skip. Before approving, he asks the AI for the hardest decision it made, the alternatives it rejected, and what it is least confident about ([Every](https://every.to/source-code/i-stopped-reading-code-my-code-reviews-got-better)).
- **Today's `ce-code-review` (primary)** picks reviewer personas from the surface the diff touches. Correctness always runs; security, migrations, API contract and others run only when touched. Depth has three paths, lite, focused and full, chosen "by consequence". "Auth, money, and externally consumed public-contract boundaries" always get the full review, as do migrations and executable non-test changes of 200 lines or more. An adversarial cross-model pass runs on "evidenced risk of unauthorized access or disclosure, financial loss, persistent data corruption or loss, irreversible external effects, or substantial service disruption". Trivial automated PRs (lockfile or version bumps) are skipped ([guide](https://github.com/EveryInc/compound-engineering-plugin/blob/main/docs/guides/ce-code-review.md)).
- **Cost data (primary).** On a real run, a 56-line executable change paid for the full spine: about 12.5M cache-read tokens in the orchestrator alone, for two findings. Their lesson: "Cost scales with the spine, not the diff … A size floor may only force full, never award lite" ([solution doc](https://github.com/EveryInc/compound-engineering-plugin/blob/main/docs/solutions/skill-design/review-cost-is-in-entering-the-spine-not-the-findings.md)).
- **Repo-owned facts:** `CODING_STANDARDS.md` holds the criteria and `REVIEW.md` the policy. The policy "is read from the base, not from the change", so a PR can't loosen its own review ([guide](https://github.com/EveryInc/compound-engineering-plugin/blob/main/docs/guides/ce-code-review.md)).

## 2. What makes the agent say "a human must look at this"

No one in this group uses an LLM's free-form "I'm unsure" as the main trigger. The triggers they do write down:

- **Irreversible or outward-facing actions.** pstack's worker rules: "Make any choice you can undo, then say what you chose and why. Stop only for a deploy, deleted data, a force-push to a shared branch, or a message to someone outside the run" ([worker.md](https://github.com/cursor/plugins/blob/main/harness/pstack/claude-code/skills/poteto-mode/worker.md)). Pocock's one-way door: migrations, data loss, mass email ([`pr` skill](https://github.com/mattpocock/skills), [talk summary](https://daily.dev/posts/fixing-the-pr-bottleneck-matt-pocock-aihero-jyn4aj6sm)).
- **Loosening a gate.** "Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green. … A disabled or soft-failed check always comes out" ([Autopilot-full](https://github.com/cursor/plugins/blob/main/harness/pstack/claude-code/skills/poteto-mode/playbooks/autopilot-full.md)).
- **Sensitive surfaces:** auth, money, public contracts, migrations, plus a size floor on executable code ([ce-code-review](https://github.com/EveryInc/compound-engineering-plugin/blob/main/docs/guides/ce-code-review.md)). These escalate review depth. They don't hand the PR to a human by default.
- **Missing or inconclusive evidence.** "If a check couldn't run, a good reply says 'inconclusive'. A confident reply without evidence is a warning sign" ([guide 06](https://github.com/cursor/plugins/blob/main/harness/pstack/claude-code/docs/guide/06-verify-and-ship.md)). Stacked PRs land only as a contiguous verified run, and the first unverified PR stops the chain ([Shipping](https://github.com/cursor/plugins/blob/main/harness/pstack/claude-code/skills/poteto-mode/playbooks/shipping.md)).
- **Feature or product-level change.** User-visible features get dogfooding, and automation is aimed at bugs, performance and maintenance ([Lightcone summary](https://www.teamday.ai/ai/roman-ugarte-lauren-tan-grok-bot-ai-coworkers-trust-ladder)).
- **Every stage may stop the line.** Triage can call a report expected behavior, repro can fail to reproduce, and "the fixer can judge the change too risky" ([guide 07](https://github.com/cursor/plugins/blob/main/harness/pstack/claude-code/docs/guide/07-overnight.md)).
- **An "Attention" section.** The morning audit has a reviewer on a different model family read the decision log and transcript and list "what deserves your scrutiny". `/ketchup` lists each pending call with its pick, evidence and risk ([guide 07](https://github.com/cursor/plugins/blob/main/harness/pstack/claude-code/docs/guide/07-overnight.md)).

## 3. What they still read

- **Evidence, not diffs:** videos, screenshots, before/after command output, the failing-then-passing test ([guide 06](https://github.com/cursor/plugins/blob/main/harness/pstack/claude-code/docs/guide/06-verify-and-ship.md); [Willison](https://simonwillison.net/2025/Dec/18/code-proven-to-work/)).
- **A short PR briefing.** pstack caps PR bodies at 40 lines with `Why`, `What changed`, `Scope`, `Tradeoffs`, `Blast Radius`, `Verification` ([opening-a-pr](https://github.com/cursor/plugins/blob/main/harness/pstack/claude-code/skills/poteto-mode/playbooks/opening-a-pr.md)). Pocock's template is Summary, Evidence, Merge Danger.
- **The decision log's Attention section,** then only the rows it points at: "You're auditing decisions, not re-reading the whole night" ([guide 07](https://github.com/cursor/plugins/blob/main/harness/pstack/claude-code/docs/guide/07-overnight.md)).
- **Architecture, dependencies, ecosystem choices** ([Steinberger](https://steipete.me/posts/2025/shipping-at-inference-speed)).
- **The system itself:** standards, lint rules, verification skills, and transcripts of failures. Klaassen aims for "half your time reviewing output, half ensuring the lesson sticks" ([Every](https://every.to/source-code/i-stopped-reading-code-my-code-reviews-got-better)). Pocock traced all 12 of his review comments on one feature to one root cause in his own standards and docs ([post](https://www.aihero.dev/watch-me-ship-a-21-000-line-feature-with-mattpocock-skills~ez95n)).
- **The product, by using it.** Pocock keeps QA for himself, and Klaassen polishes by using the app.

## 4. Failure stories they report

- **Workarounds that spread (Tan, at Cursor).** Agents bridged imperative and declarative code with `setTimeout`/`requestAnimationFrame`, justified it in comments, and the pattern spread and hurt performance. Agents pulled main-thread code into the render thread and caused jank, which led to the cross-process import ban. "Agents copy whatever the codebase already does" **(summary)**. Comments that say "Lauren said you should never do this" became a reason to ban comments ([transcript](https://sozai.app/transcript/spacex-ai-engineer-lauren-tan-part-1/)).
- **Fixes that miss the cause (Tan).** "I'd try to fix that, and it turned out that wasn't the actual problem". Without tooling, the agent "wasn't actually reading the code that I thought should be affected" ([transcript](https://sozai.app/transcript/spacex-ai-engineer-lauren-tan-part-1/)).
- **A 1,000-line change with four bugs (Klaassen).** A "simple" email signature change went through about ten versions and introduced four bugs: plain-text emails broken, CSS leaking from marketing emails, one signature per draft option, and a stale settings read that would have errored on every draft. The review swarm caught the last one ([Every](https://every.to/source-code/i-stopped-reading-code-my-code-reviews-got-better)).
- **Defensive accretion and the agent changing its own pass condition.** "A duration is not a finish condition" and "the finish condition never quietly relaxes to declare victory" ([guide 07](https://github.com/cursor/plugins/blob/main/harness/pstack/claude-code/docs/guide/07-overnight.md)). Ronacher: "if each iteration adds another small defense, the system slowly becomes less understandable while appearing more robust" ([The Coming Loop](https://lucumr.pocoo.org/2026/6/23/the-coming-loop/)).
- **Long sessions degrade (Pocock).** "The agent just produces worse work in the dumb zone" ([post](https://www.aihero.dev/watch-me-ship-a-21-000-line-feature-with-mattpocock-skills~ez95n)). Steinberger: Opus "often doesn't read the whole file", and Codex sometimes "reverts or modifies the edits" ([blog](https://steipete.me/posts/2025/shipping-at-inference-speed)).
- **The auto-merge rule merged a stranger's PR (a lesser-known solo dev).** Anton Shubin's rule was "merge when the reviewer agent passes". An outside account copied an agent-filed issue's fix line for line, and the agent merged it under his account with a reviewer `PASS`. He didn't notice for three weeks. The fixes: merge only PRs the Factory itself authored, treat outside content as data, and give agents a distinct identity ([dev.to](https://dev.to/anton_shubin_f26b3cb5a572/my-ai-agent-merged-a-strangers-pull-request-and-i-didnt-notice-for-three-weeks-4mb8)). This is a single self-reported post, not corroborated.
- **Loss of comprehension (counterpoint).** Ronacher doesn't trust unread code for lasting software. Teams risk merging "code they cannot fully explain", and "looping is powerful but it removes responsibility more and more" ([The Coming Loop](https://lucumr.pocoo.org/2026/6/23/the-coming-loop/)).

## Implications for fliesswerk's pipeline

These are inferences from the sources above, not decisions.

1. **Add a verify Step with its own agent, separate from review.** Every high-trust setup separates the agent that writes from the agent that judges, and makes the judge run the change rather than read it. Green CI plus a bot review "are not verdicts". fliesswerk has implement → review, and nothing that runs the change. This lines up with "Verification beyond tests" on the map.
2. **Pin the verdict to a patch, and have the Factory check it in code.** pstack's `git patch-id` rule is fully programmatic. The Factory can decide whether a merge-queue conflict resolution or a CI fix invalidates the verdict, then scale re-verification: a single re-check for rebases and conflicts, none for wording-only changes, and a full pass only for new behavior.
3. **Derive Human review required from reversibility and surface, mostly in code.** The triggers that recur: one-way doors (migrations, data deletion, deploys, outward messages), loosening a gate (Feedback commands, CI config, lint config, Protected paths, allowlists, budgets), sensitive surfaces (auth, money, public contracts), and missing or inconclusive evidence. Most of these are path or diff facts the Factory can compute. An agent adds a door and blast-radius judgment as a Risk reason (Pocock's `Merge Danger`). The Factory should not rely on the agent's free-form confidence.
4. **Size review depth by consequence, not diff size, to control cost.** Compound engineering measured that cost scales with entering the full review, not with the diff. Their fix was a consequence gate where size can only *force* depth, never award a cheap path. This fits fliesswerk's "the Factory scales rigor itself" position with no user-chosen modes.
5. **Read review policy from the base, never from the change.** A Ticket that edits coding standards, lint config or review instructions must be reviewed under the old ones. This is a cheap, deterministic guard against an agent weakening its own gate.
6. **Make the PR body evidence-first and short.** Use Summary, Evidence (before/after) and Merge Danger (door, blast radius), plus a Factory-written Attention list from the run's log. This is what the humans in this group actually read.
7. **Turn every human correction into a deterministic check.** All four practitioners do this. It supports the map's Learning loop: the Factory proposes lint rules and Coding standards, not more prompt prose.
8. **Scope auto-merge to the Factory's own work.** Opt-in auto-merge must cover only PRs the Factory opened on its own branches. Anything authored elsewhere is data, not instructions.
